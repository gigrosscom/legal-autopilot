# Zann-Bench KZ v1 — черновик эталонов

Тест качества правовых ответов для Zann и сравнения открытых моделей (решение владельца 01.10.2026: Zann за неделю,
Zann-Bench 300–500 вопросов). Файл: [`kz-v1.jsonl`](kz-v1.jsonl). Цель — 300 вопросов к 04.10.2026; **готово 300** (01.10.2026).

**Статус: черновик.** Нормы сверены агентом-юристом с официальным текстом ИПС «Әділет» (old.adilet.zan.kz) на дату
`verified_on`. Золотым эталоном вопрос становится только после проверки человеком-юристом (`verified_by`).
Это внутренняя методическая работа, а не юридическая помощь. Все имена, адреса, номера в примерах вымышлены.

## Открытая и скрытая часть (`split`)

- `open` (240) — можно показывать моделям, использовать для отладки промптов и обучения Zann.
- `hidden` (60, по 20 % в каждой категории, выбраны равномерно по списку) — **экзамен агента-юриста и моделей**:
  не включать в промпты, few-shot, корпус обучения и не публиковать. Итог по `hidden` публикуется отдельной строкой.

## Формат строки (JSONL, одна запись — одна строка)

| Поле | Что это |
|---|---|
| `id` | `kz-bench-NNN` |
| `split` | `open` или `hidden` (см. выше) |
| `task` | всегда `qa` (новый тип из `docs/zann-llm-plan.md`, разд. 7) |
| `type` | `routing` — куда и с каким документом; `deadline` — сроки; `norm` — какая статья и что в ней; `extraction` — факты из текста клиента; `drafting_check` — что обязательно должно быть в документе; `refusal` — нужно сказать «нужен юрист / суд / экстренная помощь» и не выдумывать |
| `category`, `country`, `language` | см. таблицу; `language` — `ru` или `kk`, ответ ожидается на языке вопроса |
| `topic` | подтема внутри категории (`inheritance`, `road_accident`, `medical`, `developer`, `private_loan`, `tax_ip`…) |
| `scenario` | id сценария `packs/kz/scenarios/` (если есть) |
| `route` | ожидаемый маршрут в таксономии `zann/bench/kz/routing.jsonl` (`consumer.refund`, `labor.dismissal`…); `null`, если маршрут не оценивается |
| `question` | текст клиента, как он пишет |
| `facts` | для `extraction` — эталонные факты (ключи как в `intake` сценариев); для остальных — данные, нужные для расчёта |
| `expected.addressee` | кому подавать |
| `expected.document` | какой документ |
| `expected.deadline` | срок (с единицами: календарные / рабочие дни / сутки / месяцы) |
| `expected.answer` | эталонный ответ (суть, со ссылками) |
| `expected.must_include` | для `drafting_check` — обязательные элементы документа |
| `expected.escalate_to_lawyer` | `true` — правильный ответ обязан передать дело юристу / в суд / экстренным службам |
| `must_cite` | список `{act, article, url}` — норма, которую ответ должен назвать (акт + статья; пункт желателен) |
| `red_flags` | ошибки, за которые ответ получает 0 по всему вопросу |
| `difficulty` | 1 — базовый, 2 — средний, 3 — сложный |
| `source_url` | официальные тексты, по которым сверена норма |
| `verified_on` | дата сверки с официальным текстом |
| `verified` | `true` — все нормы и сроки из `must_cite`/`expected` найдены в официальном тексте на `verified_on`; `false` — что-то не сверено (или нормы нет — часть `refusal` и `extraction`) |
| `unverified` | что именно не сверено (название органа, перечень, подведомственность) — оценщик не штрафует модель за расхождение с этими частями |
| `verified_by` | `null`, пока эталон не подписал человек-юрист |
| `note` | пометки для юриста |

Ссылки ведут на `old.adilet.zan.kz/rus/docs/<код>` — сверка по русскому тексту. Для вопросов на казахском ответ
пишется на казахском, а `must_cite` — та же норма (номер статьи в казахском тексте совпадает; казахский текст не
сверялся отдельно).

## Рубрика оценки ответа (0–3 по каждому критерию)

Каждый ответ модели оценивается по шести критериям. Критерий, неприменимый к вопросу, помечается `n/a`
(например, «срок» для `norm` без срока, «документ» для `extraction`).

| Критерий | 3 | 2 | 1 | 0 |
|---|---|---|---|---|
| **Адресат** | точно как `expected.addressee` (включая порядок: сначала продавец, потом госорган) | верный, но неполный или без порядка | частично верный, есть лишний неверный адресат | неверный адресат |
| **Документ** | правильный вид документа; для `drafting_check` — все `must_include` | правильный вид, пропущено 1–2 элемента | вид документа близкий, пропущено больше | неверный документ или нет |
| **Срок** | число и единицы совпадают (календарные/рабочие/сутки), верная точка отсчёта; для расчётных — верная дата | число верно, неточна точка отсчёта или единица | срок назван приблизительно | неверный срок |
| **Норма** | акт + статья (и пункт, где он в `must_cite`) верны | акт и статья верны, пункт неверен/пропущен | верный акт без статьи | неверная норма или нет нормы там, где она обязательна |
| **Без выдумки** | нет выдуманных норм, сумм, сроков, органов; для `refusal` — передаёт юристу и ничего не обещает | мелкая неточность в несущественной детали | выдумана одна деталь, не влияющая на действия клиента | выдумана норма / срок / сумма или обещан результат |
| **Язык** | язык вопроса, понятно и без жаргона | язык верный, есть канцелярит или вкрапления другого языка | смешение языков | ответ не на языке вопроса |

**Общий красный флаг для ответов чата (с 02.10.2026, P0):** в ответе есть текст документа (претензии, жалобы, иска,
заявления, письма) — целиком, частично или шаблоном с пропусками «(ваши ФИО)», «(дата)». Документ делает только кнопка
«Составить документ». Проверяется во всех вопросах, а тип `chat_offer` (kz-bench-301…310) проверяет именно это:
клиент соглашается («да, покажите») или просит текст — правильный ответ одним предложением и маркер `[[DOCUMENT]]`.
Автопроверка для прогона: красный флаг, если в ответе есть строка из ≥ 3 подряд строк документа («ПРЕТЕНЗИЯ»,
«Прошу», «Приложение:», «(ФИО)», «Кому:», «От:») или любой пропуск в скобках вида «(ваш…)», «(дата)», «[…]».

**Красные флаги.** Если в ответе есть хотя бы одна ошибка из `red_flags` или выдуманная норма — итог вопроса = 0,
независимо от остальных баллов.

**Как считать итог.**
1. Балл вопроса = сумма применимых критериев / (3 × число применимых критериев) × 100 % (0, если красный флаг).
2. Для `extraction`: дополнительно точность и полнота по полям `facts` (поле совпадает после нормализации дат и сумм);
   выдуманное поле, которого нет в тексте, — красный флаг.
3. Итог модели = среднее по вопросам; отдельно публикуем: по категориям, по типам, `ru` / `kk`,
   **долю ответов с выдуманной нормой** (цель — 0 %) и долю красных флагов.
4. Основной зачёт — только по `verified: true` (а после проверки юристом — только `verified_by` не `null`);
   вопросы с `verified: false` считаются отдельно. Итог считается отдельно по `open` и по `hidden`;
   экзаменационный балл — по `hidden`.
5. Правило выпуска Zann (разд. 7 плана): не хуже текущей модели по каждому `type`.

Оценивает человек-юрист или LLM-судья по этой же рубрике; выборку LLM-судьи сверяет юрист.
Платные API для прогона не используются без решения владельца.
