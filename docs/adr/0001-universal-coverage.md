## 2. Решение: три уровня покрытия

Каждое дело получает поле `coverage_level`:

| Уровень | Когда | Что делает платформа | Кто решает |
|---|---|---|---|
| **1 · verified** | Квалификатор уверенно выбрал опубликованный YAML-сценарий | Полный автопилот (как сейчас). Бейдж «Проверено юристом» — только если `reviewed_at` задан | Движок по `when` из YAML |
| **2 · universal** | Сценария нет, но таксономия определена и в реестре пакета есть подходящий форум | Документ по универсальному шаблону типа; адресат — из реестра; нормы/сроки — только из данных или «[норма: уточнит юрист]». **Всегда** `needs_review=true`, документ «ЧЕРНОВИК» доступен только после одобрения юриста | Движок по графу эскалации форумов |
| **3 · lawyer** | Сторона защиты в уголовном деле, лишение свободы, дети, сумма выше порога пакета, срок истекает, противоречия, низкая уверенность, нет форума в реестре | Досье + передача проверенному юристу (`/lawyers`) | Юрист |

Пользователь видит уровень и его смысл на экране дела, на карте пути и в каждом документе.

### Квалификация (`core/qualifier.py`)

```
текст → [экстренная проверка] → [уровень 1: ai.qualify по опубликованным сценариям]
      → если нет/низкая уверенность → [уровень 2: ai.classify_taxonomy]
      → [правила маршрутизации уровня 3 из данных пакета] → решение + confidence + объяснение
```

- `ai.classify_taxonomy` — LLM выбирает **только из перечислений** (`enum`) таксономии: отрасль, тип спора, роль заявителя, тип противной стороны, регион. Свободный текст для адресата/нормы не запрашивается вообще.
- Правила уровня 3 (`routing.yaml` пакета): роль `suspect|accused` → 3; отрасль/тип из списка `lawyer_only` → 3; `amount_at_stake > high_amount_threshold` → 3; confidence < порога → 3; нет форума → 3.
- Результат пишется в `AuditLog` (`qualified_level`, причины) и в `demand_signals` (аналитика спроса).

### Выбор форума — детерминированно

Фильтр реестра пакета по `(branch, dispute_type, applicant_role, region)`. Один кандидат → берём. Несколько → **пользователь выбирает** из списка с объяснением различий (правовой эффект, срок, способ подачи). LLM адресата не выбирает. Нет кандидатов → уровень 3.

## 3. Схема данных пакетов

Всё страновое — только в `packs/<cc>/`. В ядре — глобальный каталог отраслей (не страновой).

```
apps/api/konsilier/core/taxonomy/global.yaml   # отрасли права и типы споров (глобально)
packs/<cc>/taxonomy.yaml       # локальные расширения/уточнения
packs/<cc>/forums/*.yaml       # реестр органов и организаций
packs/<cc>/documents/*.yaml    # типы документов и обязательные реквизиты
packs/<cc>/routing.yaml        # правила уровня 3, пороги, экстренные номера, UPL, ложный донос
packs/<cc>/templates/generic/*.docx  # универсальные шаблоны по типам документов
```

### 3.1 Таксономия (pydantic, эскиз)

```python
class DisputeType(_Strict):
    id: str                      # "labor.dismissal"
    title: Localized
    applicant_roles: tuple[str, ...]   # из глобального перечня ролей
    counterparty_kinds: tuple[str, ...]
    sensitive: tuple[Literal["health", "religion", "criminal_record", "children"], ...] = ()

class Branch(_Strict):
    id: Literal["civil","criminal","administrative","commercial","family","labor","tax",
                "housing","inheritance","migration","consumer", ...]
    title: Localized
    disputes: tuple[DisputeType, ...]

class PackTaxonomy(_Strict):          # packs/<cc>/taxonomy.yaml
    extends: Literal["global"] = "global"
    add: tuple[DisputeType, ...] = ()         # локальные типы (id с префиксом cc.)
    disable: tuple[str, ...] = ()             # глобальные типы, неприменимые в стране
```

Глобальный перечень ролей: `claimant, victim, complainant, consumer, employee, employer, tenant, landlord, heir, spouse, parent, taxpayer, suspect, accused, business`.

### 3.2 Реестр форумов (`forums/*.yaml`)

```python
class Forum(_Strict):
    id: str                                   # "kz.court.district_civil"
    type: Literal["court","prosecutor","police","regulator","ministry","ombudsman",
                  "local_authority","arbitration","mediation","private_org"]
    name: Localized
    jurisdiction: ForumJurisdiction           # регион(ы), территориальная подсудность (текст+правило)
    accepts: tuple[AcceptRule, ...]           # branch / dispute_type / applicant_role
    submission: tuple[SubmissionChannel, ...] # portal(url) | email | post | in_person
    form_requirements: Localized = {}         # требования к форме
    languages: tuple[str, ...]
    fee: Fee | None                           # сумма+валюта+норма или None; нет данных → «уточнит юрист»
    response_deadline: DeadlineSpec | None    # тот же тип, что в сценариях
    appeals_to: tuple[str, ...] = ()          # граф эскалации (id других форумов)
    legal_effect: Literal["binding","advisory","none"]
    source: str                               # ссылка/документ, откуда запись
    verified_at: date | None = None           # None → TODO; пользователь видит «уточнит юрист»
    verified_by: str | None = None
```

Валидация загрузчика: уникальные id; `appeals_to` ссылается на существующие форумы; граф без циклов; у записи без `verified_at` поля `fee`/`response_deadline` помечаются TODO. Ошибки валидации не дают пакету загрузиться (как сейчас со сценариями).

### 3.3 Типы документов (`documents/*.yaml`)

```python
class DocumentType(_Strict):
    id: Literal["complaint","claim_letter","statement","lawsuit","motion","appeal","appeal_request"]
    title: Localized
    required_fields: tuple[IntakeField, ...]  # реквизиты по стране (тот же IntakeField)
    template: str                             # packs/<cc>/templates/generic/<id>.docx
    forum_types: tuple[str, ...]              # к каким типам форумов применим
    verified_at: date | None = None
```

### 3.4 `routing.yaml` пакета

- `lawyer_only`: отрасли/типы споров, всегда уровень 3 (например, `criminal.*` для стороны защиты).
- `high_amount_threshold`, `urgent_deadline_days`.
- `emergency`: номера (полиция, скорая, кризисная линия для пострадавших от насилия, линия для детей) + ключевые слова по языкам для детектора. Номера показываются и до подтверждения источника (не показать экстренный номер опаснее), но каждая запись стоит в `REVIEW.md` как TODO до подтверждения.
- `upl_notice`: правило о юридической практике без лицензии (текст + источник + статус проверки).
- `false_report_norm`: норма об ответственности за заведомо ложный донос (ссылка + статус проверки).

### 3.5 `REVIEW.md`

Генерируется командой `python -m konsilier.cli review <cc>`: таблица «запись → статус (проверено/TODO) → кем подписано → дата». Ручная часть (пояснения юриста) сохраняется.

## 4. Универсальный движок (`GenericScenario`)

Цель — **переиспользовать** существующий `CaseEngine` без форка логики.

- `core/generic.py::build_generic_scenario(pack, taxonomy_ref, forum, document_type) -> Scenario` собирает **обычный объект `Scenario`** в памяти: intake = реквизиты типа документа + общие поля; одно действие-документ к выбранному форуму; дальнейшие действия — по `appeals_to` с условиями `when` в существующем DSL (`prev.response in [none, refusal, partial]`); в конце — `handoff`.
- Id вида `generic:<cc>:<dispute_type>:<forum_id>:<doc_type>@<data version>`; в `Case.scenario_id` сохраняется этот id → `scenario_of(case)` пересобирает сценарий из данных детерминированно.
- LLM пишет только «изложение обстоятельств» и «требования» (новая задача `generic_demands`, основная модель). Нормы, сроки, пошлины, адресаты в документ подставляются только из данных. Нет данных → текст «[норма: уточнит юрист]», срок «уточнит юрист» + приоритет в очереди.
- `needs_review=true` всегда; `approval_required` для уровня 2 — всегда `true` независимо от `APPROVAL_REQUIRED_FIRST_N`. Скачивание/подача до одобрения недоступны (как сейчас для `pending_approval`).

## 5. Изменения автомата состояний (нужно согласие)

Статусы **не меняются**. Предлагаю два перехода:

```
intake    → handed_to_lawyer   # уровень 3 сразу после квалификации / экстренный маршрут к юристу
qualified → handed_to_lawyer   # уровень 3 после сбора досье без документов
```

Альтернатива без изменения автомата — держать дело уровня 3 в `intake` с флагом. Это хуже: дело «зависает», дорожная карта и списки дел показывают неверный статус.

## 6. Религиозные форумы — не поддерживаются

Решение основателя (28.09.2026): платформа ведёт дела только в государственные и признанные государством
органы (суд, прокуратура, регуляторы, омбудсмен, медиация и т. п.). Тип `religious` из реестра форумов,
выбор «религиозного порядка» в intake и связанные тексты удалены. Религия остаётся только особой
категорией персональных данных (согласие, минимум хранения), платформа её не определяет и не спрашивает.

## 7. Уголовное и административное право, безопасность

- **Экстренные ситуации** — проверка **до** intake: ключевые слова из `routing.yaml` + флаг `emergency` в ответе классификатора. Экран с номерами страны (компонент дизайн-системы), дело при этом не блокируется.
- **Потерпевший/заявитель** (уровень 2 при наличии форума): заявление о преступлении/правонарушении, жалоба на бездействие, жалоба прокурору, обжалование административного штрафа. Перед intake — предупреждение об ответственности за заведомо ложный донос (норма из пакета) и подтверждение. Подсказки intake просят факты (что, где, когда, кто видел), а не оценки («мошенник», «вор»); LLM помечает оценочные формулировки, пользователь переписывает.
- **Подозреваемый/обвиняемый** — только уровень 3: досье и срочная передача адвокату. Задачи LLM для документов защиты не существует в коде.
- **Детектор злоупотреблений** (`core/abuse.py`): счётчики по нормализованному ответчику (частное лицо) и заявителю за окно; повторные/массовые жалобы; LLM-флаги `harassment|blackmail|defamation|knowingly_false` (только флаг, не решение) → дело в статус проверки (`needs_review` + причина `abuse_suspected`), документы недоступны до решения администратора. Пороги — в `routing.yaml`.
- **Особые категории данных** (здоровье, религия, судимость): явное согласие (`Consent` в БД), хранение минимума, PII-редакция `core/pii.py` применяется ко всем новым задачам LLM без исключений.
- **Юридическая практика без лицензии**: текст `upl_notice` из пакета — постоянный компонент на экране дела и в документах уровня 2.

## 8. БД и API

Миграция Alembic `0004_universal_coverage`:
- `cases`: `coverage_level` (`verified|universal|lawyer`, default `verified` для существующих), `taxonomy` JSON, `forum_id`, `route_reasons` JSON.
- `demand_signals`: страна, отрасль, тип спора, уровень, дата — без PII.
- `consents`: вид согласия, дело, время.
- `forum_drafts`: черновики правок реестра из админки (см. ниже).

API (обратная совместимость сохраняется, существующие ответы только расширяются):
- `GET /v1/coverage` — страны × отрасли со статусами (из данных пакетов).
- `GET /v1/forums?country=&branch=` — публичный реестр (только поля для пользователя).
- `POST /v1/cases/{id}/forum` — выбор форума пользователем из кандидатов.
- Админка: очередь уровня 2 (`/v1/admin/review-queue`), реестр форумов: просмотр + черновики правок.

**Редактирование реестра в админке.** Источник истины — YAML в git (проверка юристом, история, ревью). Админка сохраняет правку как черновик в `forum_drafts`; команда `python -m konsilier.cli forums export` превращает черновики в YAML-патч для PR. Прямой записи в YAML на сервере нет — иначе правки теряются при деплое и обходят ревью.

| Стоимость LLM | Задачи уровня 2 на быстрой модели, кроме текста документа |

## 12. Что не входит в объём

- Содержание пакетов других стран (только схема и тестовый пакет `xx`).
- Автоматическая подача документов уровня 2 (только после одобрения юриста и вручную пользователем).
- Документы защиты по уголовным делам.
- Голосовой ввод, безопасная сделка/эскроу, оплата.
- Религиозный форум с правовым статусом — до вашего решения по стране и специалисту.
- Юридическая проверка норм KZ — делает юрист по `REVIEW.md`.

## 15. Дополнения к объёму (27.09.2026)

**Канбан дел и задач.** Каждое дело — карточка на доске; колонки — этапы жизненного цикла, а не новые статусы:
«Заявка» (`intake`) → «Данные собраны» (`qualified`) → «Документ готов» (`action_ready`) → «Подано, ждём ответ»
(`submitted`, `awaiting_response`) → «Эскалация» (`escalated`) → «У юриста» (`handed_to_lawyer`) → «Решено» (`resolved`).
Карточка никогда не исчезает: закрытые дела остаются в «Решено». Внутри карточки — задачи (документы, сроки, одобрения)
со своими статусами. Доска у пользователя («Мои дела») и у администратора (все дела, фильтр по уровню покрытия
и очереди проверки). Порядок колонок и подписи — из автомата состояний, без отдельной логики.

**Языки en / ar / tr.** Интерфейс сайта на ru, kk, en, ar, tr; арабский — справа налево (`dir="rtl"`,
логические CSS-свойства, шрифт с арабскими глифами через `next/font`). Язык пакета добавляется в пакет страны
вместе с переводами его текстов; ядро языков не знает.

**Страны СНГ и MENA.** Пакеты создаются по той же схеме. Нормы, органы, сроки и пошлины не генерируются: пока нет
проверенных данных, у страны статус `planned` — на `/coverage` она показывается как «скоро» с листом ожидания,
дела по ней не принимаются. Наполнение — юристами страны по `REVIEW.md` (или из официальных источников, если к ним
будет открыт доступ из среды разработки).
