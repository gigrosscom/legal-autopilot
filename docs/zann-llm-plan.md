## 1. Коротко

1. Сначала учим модель **находить и цитировать** закон (RAG). Дообучение — потом.
2. Закон модель не «запоминает». Нормы и сроки она берёт только из найденного официального текста.
3. База — открытая модель с **коммерческой** лицензией. Главный кандидат — **Qwen3.5-9B-Kazakh** от ISSAI
   (Apache 2.0, вышла 05.08.2026).
4. Качество меряем своим тестом Zann-Bench. Эталонные ответы проверяет владелец-юрист.
5. Модель выходит в продукт, только если на Zann-Bench она не хуже текущей.
6. Первый шаг уже сделан: сборщик корпуса законов `tools/zann/collect_laws.py` (раздел 4).

## 4. Первый шаг: сборщик корпуса законов (сделан 30.09.2026)

`tools/zann/collect_laws.py`:

В ТК на обоих языках по 227 статей, то есть версии совпадают по структуре.

## 4а. Сбор корпуса на сервере (задача «zann-corpus»)

**Как.** Модуль `apps/api/konsilier/zann/corpus.py`. ИИ не вызывается, платных сервисов нет: обычные HTTP-запросы к
серверному зеркалу old.adilet.zan.kz, с паузой между запросами одного потока (по умолчанию 3 с, минимум 2 с), с
повторами при 429/5xx. Перед каждым запуском читается robots.txt зеркала. Если он закроет нужные страницы, сбор
останавливается.

**Ускорение (решение 01.10.2026: весь корпус к 04.10).** `ZANN_CORPUS_CONCURRENCY` потоков (по умолчанию 1 — как
раньше) делят один общий лимит `ZANN_CORPUS_RATE` запросов в секунду на всех (по умолчанию 0,5, потолок 3; если в
robots.txt есть Crawl-delay и он больше — действует он). Ответ 429 или 503 ставит на паузу все потоки сразу
(Retry-After, иначе нарастающая пауза); три ошибки подряд по всем потокам завершают запуск, как раньше. Каждый поток
забирает акт из очереди условным UPDATE (`state` → `busy`; в PostgreSQL кандидат читается `FOR UPDATE SKIP LOCKED`),
поэтому один акт не читается дважды — ни двумя потоками, ни двумя контейнерами API. Забранный акт, брошенный упавшим
запуском, через час возвращается в очередь. Указатель обходит один поток за раз.

**Поиск актов.** У зеркала есть открытый для роботов указатель `/rus/index/docs/…`. Разделы `/rus/search/` и
`/rus/list/docs/` robots.txt закрывает, и мы их не трогаем. Указатель принимает фильтры поиска: статус
(`st=new|upd` — действующие, `st=yts|stp` — утратившие силу), вид акта (`va=КОД`, `ЗАК`, `ПОСТ` …) и
`pagesize=100`. Каждая страница даёт код, название, статус и строку вида «Закон РК от … № …». Замер 30.09.2026:

| | Всего в базе | Действующие |
|---|---:|---:|
| Все акты | 230 933 | 132 862 |
| Кодексы (КОД) | 55 | 25 |
| Конституция, конституционные законы, указы с силой конст. закона | 3 + 93 + 3 | 1 + 87 + 1 |
| Законы (ЗАК) и указы с силой закона (УЗАК) | 3 532 + 72 | 3 191 + 52 |
| Указы (УКАЗ) | 4 296 | 3 347 |
| Постановления (ПОСТ) | 81 071 | 43 920 |
| Приказы (ПРИК) | 32 048 | 18 679 |
| Распоряжения (РАСП) | 5 563 | 4 765 |
| Решения (РЕШ, в основном маслихатов и акиматов) | 103 687 | 59 015 |

У одного акта бывает несколько видов (например, «Постановление» и «Изменения»). Поэтому сумма по видам больше
общего числа.

**Очередь.** Сначала кодексы, Конституция и конституционные законы, затем законы, затем нормативные постановления
Верховного Суда (отдельный вид `НПВС`: фильтр указателя `va=НПОС&kv=1_105`, где `kv=1_105` — орган «Верховный Суд
Республики Казахстан»; 215 действующих на 01.10.2026, персональных данных в них нет), затем указы, постановления,
приказы и распоряжения, затем всё остальное действующее (одним общим списком). До 01.10.2026 разбор указателя
пропускал коды с буквой в конце (`P260000007S` — постановления ВС, `H19EK000237` …); после обновления указатель один
раз обходится заново с первой страницы, а известные акты получают новые приоритеты. Утратившие силу собираются только если так
задано в настройках, и после всех действующих. Состояние хранится в базе: `zann_acts` (очередь и статус акта),
`zann_files` (сохранённые тексты), `zann_listings` (до какой страницы дошёл обход указателя). Каждый запуск
продолжает с места, где остановился предыдущий.

**Где лежит.** Тексты хранятся в том же хранилище, что и документы (Object Storage или локальный диск):
`zann/corpus/<код>.<ru|kk>.txt.gz`. Там же лежит `zann/corpus/manifest.jsonl.gz` — по строке на файл: код, название,
вид, статус, язык, URL, дата, sha256, число символов, размер. Манифест переписывается в конце каждого запуска, в
котором что-то изменилось. Если казахского текста нет (страница kk отдаёт русский текст), файл kk не сохраняется.

**Обновление.** Раз в `ZANN_CORPUS_REFRESH_DAYS` (30) дней указатель обходится заново. Акты с изменившимся статусом,
названием или строкой описания снова встают в очередь. Когда очередь пуста, заново читаются самые старые тексты.
Файл выгружается повторно только если изменился его sha256. Условный GET не помогает: зеркало не отдаёт ETag, а
Last-Modified у него всегда равен текущему времени.

**Сколько времени.** На каждый акт уходит 2 запроса (ru и kk), это ≈ 6–7 с при паузе 3 с.
- Кодексы, конституционные акты и законы (≈ 3 400 актов, вариант «Б») — ≈ 6–7 часов непрерывного сбора.
- Указы, постановления, приказы, распоряжения (≈ 70 тыс.) — ≈ 5–6 суток непрерывно.
- Все действующие (≈ 133 тыс.) — ≈ 10–11 суток непрерывно, или около 10 месяцев, если собирать только по 50 минут
  ночью.

Поэтому для полного корпуса нужен непрерывный режим (`ZANN_CORPUS_HOUR=-1`). Ночной режим годится для обновлений.

**Как включить** (настройки сервера, `deploy/env.example`):
```
ZANN_CORPUS_ENABLED=true
ZANN_CORPUS_HOUR=-1          # сразу и непрерывно; 2 — только ночью 02:00–02:50 (до обхода библиотеки в 03:00)
ZANN_CORPUS_MINUTES=50       # длина одного запуска
ZANN_CORPUS_PAUSE=3          # секунд между запросами одного потока, минимум 2
ZANN_CORPUS_CONCURRENCY=1    # потоков; для быстрого сбора 8
ZANN_CORPUS_RATE=0.5         # запросов в секунду на все потоки вместе, потолок 3; для быстрого сбора 2
ZANN_CORPUS_LANGS=ru,kk
ZANN_CORPUS_STATUSES=in_force   # in_force,lost — ещё и утратившие силу (≈ 98 тыс.), после всех действующих
```
Вручную: `python -m konsilier.cli zann-corpus --discover` обходит только указатель, без текстов.
`python -m konsilier.cli zann-corpus --limit 50 --minutes 30` собирает не больше 50 актов и не дольше 30 минут.
Ход сбора виден в `/v1/admin/metrics` → `zann`: акты по статусам и видам, число файлов, байты, символы, темп —
`requests_last_hour` (запросов к порталу за час), `acts_last_hour`, `files_last_hour`, `acts_busy` (в работе).

**Стоимость ≈ 0.** Вызовов ИИ нет, трафик входящий. Хранение в Yandex Object Storage: первый 1 ГБ в месяц бесплатно,
дальше ≈ 17 ₸ за ГБ в месяц. Ожидаемый объём ≈ 0,5 ГБ в gzip, то есть в пределах бесплатного гигабайта. Копия в
закрытом наборе Hugging Face — бесплатно (до 100 ГБ).

**Условия портала.** На 30.09.2026 в robots.txt нового сайта adilet.zan.kz есть раздел «Обучающие ИИ-краулеры».
Сайт закрывает себя для GPTBot, ClaudeBot, CCBot, Google-Extended и других ботов с формулировкой «массовая выкачка
корпуса на обучение модели». На зеркале old.adilet.zan.kz, которое читает наш сбор, такого раздела нет: указатель и
страницы актов открыты для всех роботов. Наш User-Agent честно называет цель («Zann corpus collector»). Решение
владелец принял как юрист. Перед включением сбора этот раздел robots.txt нужно показать ему.

## 4б. Zann 1 — «ищет и цитирует» (сделано 01.10.2026, ветка `claude/zann-search`)

Решение владельца: поиск — бесплатный (01.10.2026: Zann за неделю, до 08.10). Платных API нет, GPU не нужен.

**Индекс статей.** Собранные акты (раздел 4а) режутся на статьи тем же разбором, что у юридического агента
(«Статья N.» / «N-бап.»; статья кончается на следующей статье или главе). Акты без статей (постановления, приказы)
режутся на куски по ≈4 000 знаков, без номера статьи. Очень длинная статья хранится частями с тем же номером.
Таблица `zann_articles` (миграция **0028**: номера 0026 и 0027 заняты в ветках `claude/team-delivery` и
`claude/team-eotinish-bridge`; какая ветка сольётся позже — та ставит свой `down_revision` на предыдущую голову).
В строке: код акта, название, вид, статус, язык, номер и заголовок статьи, текст, ссылка на old.adilet.zan.kz с
переходом к статье (`#:~:text=Статья%20113.` — у зеркала нет якорей у статей, браузер сам прокручивает к тексту).

**Обновление.** Задача раз в 30 минут и сразу после каждого запуска сбора; за раз — до 10 минут. Заново режутся
только новые файлы и файлы с другим sha256 или статусом акта (`zann_indexed`); удалённые из корпуса — убираются.

**Поиск** (`konsilier/zann/search.py`):
1. Прямая ссылка в вопросе — «ст. 113 ТК», «статья 9 Закона о защите прав потребителей», «Еңбек кодексінің
   113-бабы» — находит статью по номеру и акту сразу.
2. Полнотекстовый PostgreSQL: колонка `tsv` (конфигурация `russian` для ru, `simple` для kk) с GIN-индексом. Сначала
   статьи со всеми словами вопроса, затем со всеми, кроме одного, затем с любым (каждый шаг — не больше 500
   совпадений, запрос — не дольше 400 мс). Порядок — по словам в заголовке статьи и тексте с поправкой на длину;
   кодексы и законы выше подзаконных актов, утратившие силу ниже.
3. По желанию — семантический (`ZANN_EMBEDDINGS=e5-small`, модель intfloat/multilingual-e5-small, MIT, 118 млн
   параметров, работает на CPU сервера; векторы — в той же таблице, косинус в памяти, pgvector не нужен) и слияние
   списков (reciprocal rank fusion). По умолчанию выключен.

**Где работает.**
- `GET /v1/zann/search?q=&lang=ru|kk&limit=` — для админки и бота (X-Admin-Token или X-Bot-Secret): статьи с
  цитатой «ст. 113, Трудовой кодекс Республики Казахстан» (kk: «113-бап, …»), ссылкой и выдержкой.
- **Чат** (настройка `ZANN_SEARCH_CHAT`, по умолчанию включена): до ответа модели в контекст идут 3 лучшие статьи
  для последнего сообщения, и у модели есть инструмент `law_search`. Модель цитирует «ст. N <акт>» со ссылкой;
  такие статьи считаются прочитанными при проверке названных в ответе норм. В чате — только поиск по словам
  (миллисекунды), без семантики. Статью целиком чат по-прежнему берёт из нашей копии (раздел 4а), живой портал — только
  для актов, которых ещё нет в корпусе.
- Консоль: `python -m konsilier.cli zann-index`, `zann-search "…"`; счётчики — `/v1/admin/metrics` → `zann_index`.

**Замеры 01.10.2026** (локальный PostgreSQL 16, 4 vCPU, параллельно шли тесты других сессий):

| Что | Результат |
|---|---|
| Разрезка 21 акта сценариев KZ (42 файла ru+kk, 45 МБ текста) | 12 087 статей за 12,8 с; число статей ru и kk совпадает (ТК — 227 и 227) |
| Поиск по словам, 12 тыс. статей, 15 вопросов ru/kk | p50 12 мс, максимум 36 мс |
| Поиск по словам, 302 тыс. статей (те же акты ×25 — объём кодексов и законов, ≈1,35 ГБ с индексом) | p50 22–27 мс, худший вопрос 140–200 мс |
| Прямая ссылка «ст. 113 ТК» | 3–4 мс |
| e5-small на CPU (под нагрузкой) | ≈4 статьи/с на векторизацию, ≈0,9 с на вопрос |

Вывод по семантике: на CPU сервера e5-small слишком медленный для чата (≈1 с на вопрос) и для всего корпуса
(300 тыс. статей ≈ 20 часов). Поэтому по умолчанию — только поиск по словам. Векторы всего корпуса разумно посчитать
на бесплатном GPU (Kaggle / Colab) и загрузить в таблицу; тогда семантика нужна только для API и Zann-Bench.
Качество по словам хорошее, когда в вопросе есть юридические слова («испытательный срок», «алименты»,
«апелляционная жалоба»); на бытовых формулировках («сдать обратно куртку») оно слабее — это цель для семантики и
для Zann-Bench.

**Zann-Bench на открытых моделях** — `tools/zann/bench_run.py` (инструкция и формат вопроса — в
[tools/zann/README.md](../tools/zann/README.md)): модели NVIDIA API Catalog (Qwen, Llama, Gemma, Nemotron) отвечают
с нашим поиском и без него; считаются верная цитата, выдуманные нормы, пересечение с эталоном, время. Лимит
каталога — до 40 запросов в минуту, скрипт его соблюдает. Ключ — `NVIDIA_API_KEY` из среды. Прогона на моделях
ещё не было: нужен ключ на сервере и вопросы с эталонами (`team/zann/bench/kz-v1.jsonl`).

## 5. Разметка

- **Инструмент — Label Studio** (Apache 2.0, активно развивается, ставится у нас, данные не уходят). Argilla тоже
  подходит, но её авторы больше не добавляют новые функции (README репозитория, проверено 30.09.2026).
- **Что размечаем:**
  1. Zann-Bench: маршрут спора, факты из документа, вопрос → эталонный ответ со ссылкой на статью.
  2. Обучающие примеры: запрос → образцовый ответ или документ.
  3. Оценки ответов модели: лучше / хуже (для preference tuning в Zann 2).
- **Кто:** владелец-юрист проверяет и ставит имя в `verified_by`. Казахские задания — ещё и носитель языка.
- **Формат:** JSONL, как в `zann/bench/kz/`.

## 6. RAG или дообучение

**Рекомендация: сначала RAG.**

| | RAG (поиск по официальным текстам) | Дообучение (LoRA) |
|---|---|---|
| Закон меняется | Берём действующую редакцию | Модель помнит закон на дату обучения |
| Точная ссылка на статью | Да, со статьёй и URL | Модель может придумать норму |
| Стоимость | Без GPU и без разметки | GPU и сотни размеченных примеров |
| Чему учит | Знанию закона | Форме: язык, стиль, маршрут, JSON |

Порядок:
1. **RAG.** Индекс статей всех собранных актов (ru и kk) в нашем PostgreSQL — сделан 01.10.2026, раздел 4б. Живое открытие статьи на adilet остаётся
   источником истины, индекс подсказывает, какую статью открыть.
2. **LoRA/QLoRA** — только для формы: понимание ru/kk/шала-қазақ, маршрут спора, извлечение фактов, стиль документа.
3. Закон в веса модели не «зашиваем» никогда.

## 7. Оценка

**Zann-Bench (KZ)** — наш тест. Сейчас в нём 22 задания маршрута и 3 задания извлечения; юрист не проверил ни одного.

Добавляем тип **`qa`** — правовой вопрос с эталонным ответом:
- поля: вопрос, язык, эталонный ответ, акт и статья (код adilet + номер), `verified_by`;
- эталонные ответы пишет команда, **проверяет и подписывает владелец-юрист**;
- цель к 31.12.2026 — 200 проверенных заданий, из них не меньше трети на казахском (оценка);
- цель к 30.06.2027 — 500.

Что меряем:
1. **Маршрут** — точность отнесения к спору.
2. **Извлечение** — точность и полнота фактов.
3. **Ссылка** — модель сослалась на правильную статью правильного акта.
4. **Выдуманные нормы** — доля ответов с нормой, которой нет в найденном тексте. Цель — 0.
5. **Качество ответа** — юрист оценивает выборку по шкале 1–5; на остальных — LLM-судья по той же шкале
   (сверяем с юристом).

Сравниваем: текущий прод (Gemini), Qwen3.8-27B (Cerebras), Qwen3.5-9B-Kazakh, KazLLM (только для исследования).

Правило выпуска: не хуже текущей модели по каждому типу заданий.

- Корпус законов и выгрузки в git не коммитим (`data/` в `.gitignore`).
- Эксперименты логируем в свой MLflow, а не в сторонний сервис.
- В моделях и наборах на Hugging Face — только приватный доступ.
- Юрист выборочно проверяет обезличенные примеры: одного маскирования ИИН и телефонов может не хватить.
