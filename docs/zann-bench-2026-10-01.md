# Zann-Bench KZ v1 — открытые модели NVIDIA API Catalog, 01.10.2026

Задача менеджера проекта (решение владельца 01.10, неделя Zann): прогнать открытые модели из NVIDIA API Catalog на
Zann-Bench и получить оценки по категориям. Бесплатный уровень каталога (≤ 40 запросов/мин), платные API не
использовались.

## Главное

1. **Ни одна открытая модель «из коробки» не готова отвечать клиентам без нашей проверки.** Лучший автоматический итог —
   67 % (Nemotron 3 Ultra с поиском), но строгий LLM-судья обнуляет большую часть ответов Nemotron/Llama/gpt-oss за
   выдуманные или неверные детали (срок «10 рабочих» вместо «10 календарных», не та статья, право РФ).
2. **Самая «осторожная» — Gemma 4 31B**: итог 60 % без поиска / 63 % с поиском, 0 % выдуманных норм по автоматической
   проверке и лучший итог с судьёй среди моделей с полным прогоном (43 %). Она редко называет статьи (норма 23–29 %) —
   поэтому реже ошибается. Kimi K3 показал лучшие цифры (66 % / 50 % с судьёй), но каталог отдал только **61 из 240**
   ответов (429 — лимит модели), это не сравнимо с остальными.
3. **Поиск по нашему корпусу помогает, но слабо, потому что сам поиск пока слабый.** Он нашёл нужную статью
   (`must_cite`) в топ-5 только для **21 %** вопросов. Там, где нашёл, модели цитируют верно (пример 1). С поиском:
   Nemotron Ultra 61 → 67 %, норма 25 → 36 %, сроки 52 → 59 %; Gemma 60 → 63 %, норма 23 → 29 %, сроки 14 → 32 %.
   Главный рычаг качества сейчас — поиск (ранжирование, синонимы, семантика), а не выбор модели.
4. **Казахский язык слабее на 5–12 пунктов** у всех моделей (Gemma 62 → 51, Llama 57 → 46). Модели отвечают
   по-казахски (язык ≈ 100 %), но текст местами неграмотный (пример 4).
5. **Типовые выдумки**: «Жилищный кодекс РК» (такого кодекса нет — это кодекс РФ; у нас Закон «О жилищных отношениях»),
   ссылки на ГК РФ / Росреестр / ЕГРН, несуществующие статьи ГПК (617, 646) и ЗПП (48, 57, 71). Без поиска модели
   выдумывают нормы в 0–4 % ответов (автоматическая проверка, нижняя граница), по мнению судьи — в 17–63 %.
6. Задержки на бесплатном уровне большие и нестабильные: p50 15–48 с на ответ, p95 до 136 с. Для чата (KPI «3 минуты
   до документа») бесплатный каталог годится только для офлайн-оценки, не для продакшена.

## Как считали

**Автоматическая оценка** (`tools/zann/bench_run.py`, функция `score`) — простые правила, без ИИ:

| Критерий | Когда применяется | Как считается |
|---|---|---|
| Норма | есть `must_cite` | для каждой нормы: названы акт **и** номер статьи → 1; назван только акт → ⅓; иначе 0. Ссылки разбираются в обоих порядках («ст. 30 ЗПП», «ЗПП ст. 30», «Еңбек кодексінің 113-бабы»), с сокращениями (ТК, ГК, ГПК, АППК, КоАП, ЗПП, АК, ӘРПК…). Две части ГК — один акт. |
| Адресат | `routing`, `refusal` | классы адресатов из `expected.addressee` (продавец, работодатель, суд, инспекция труда, прокуратура, акимат, банк, АРРФР, нотариус, eOtinish, ЦОН, юрист, экстренные службы…; ru + kk), доля найденных в ответе. |
| Документ | `routing`, `drafting_check` | так же по классам документов (претензия, жалоба, иск, заявление, обжалование, уведомление…). |
| Срок | `deadline`, `routing` | пары «число + единица» из `expected.deadline` (с «рабочих»/«календарных», числа словами ru/kk) — доля найденных в ответе. |
| Обязательные элементы | `drafting_check` | элемент `must_include` найден, если в ответе есть ≥ половины его ключевых основ. |
| Факты | `extraction` | значения `facts` (даты в разных записях, суммы без пробелов, слова по основам). |
| Передача юристу | `escalate_to_lawyer = true` | в ответе есть юрист/адвокат/суд/экстренные службы. |
| Язык | всегда | ответ на языке вопроса (для kk — доля слов с ә ғ қ ң ө ұ ү һ і ≥ 15 %). |
| **Выдуманная норма** → итог 0 | всегда | статья, которой нет в нашем корпусе для названного акта (и для актов, названных рядом); акт, которого в РК нет («Жилищный кодекс»); ссылка на право РФ; для `extraction` — ИИН/БИН, которого нет в тексте клиента. |

Итог вопроса — среднее применимых критериев (0, если есть выдуманная норма); итог модели — среднее по вопросам.
Эталоны бенча, прогнанные через тот же оценщик, получают 96 % — шкала откалибрована сверху.

**LLM-судья** (`--judge`, все цифры с пометкой «судья (LLM)»): `google/gemma-4-31b-it`, temperature 0, читает вопрос,
эталон (с адресатом, документом, сроком и пометками `unverified`), красные флаги и ответ; возвращает JSON — какие
флаги нарушены и есть ли выдуманная норма/срок/сумма/орган. Второй судья `nvidia/nemotron-3-super-120b-a12b` — на
выборке 145 ответов (совпадение 76 %).

**Поиск** — `LawIndex.search(вопрос, prefer_lang=язык, limit=5, semantic=False)`, как в чате, по локальной SQLite-копии
индекса; в промпт идут 5 статей (до 1500 знаков каждая) с кодом акта, номером и ссылкой.

## Ограничения — читать перед выводами

- **Эталоны ещё не проверены юристом** (`verified_by` пуст у всех): нормы сверены агентом-юристом с текстом «Әділет».
  Основной зачёт по README — `verified: true` (224 вопроса); он отличается от общего итога на 1–2 пункта (таблица ниже).
- **Автоматическая оценка — по ключевым словам.** Она не понимает смысла: верный по сути ответ без номера статьи
  теряет баллы, а ответ с правильными словами и неверной логикой может их получить. «Выдуманные нормы, авто» — нижняя
  граница: проверяются только акты из нашего корпуса и известные «чужие» акты.
- **Судья — тоже модель**: он ошибается (пример 1 — объявил выдумкой действующее название закона), строже к
  конкретным деталям и, возможно, мягче к своей модели (Gemma). Цифры судьи — для сравнения моделей между собой, не
  абсолютная оценка.
- **Промпт чата запрещает называть статьи по памяти** («never state an article number… from memory»); мы смягчили это
  правило для бенча, но модели всё равно часто называют только закон. Поэтому «Норма» без поиска низкая у всех — это
  отчасти следствие нашего же промпта.
- **Поиск — SQLite-путь** (ранжирование в Python по всем статьям), на сервере — PostgreSQL full-text с теми же
  весами; результаты близки, но не идентичны. Векторный поиск (ZANN_EMBEDDINGS) не включался.
- **Корпус полный для бенча** (все 406 норм `must_cite` есть), но собран под вопросы бенча — на реальных вопросах
  клиентов, где нужны другие акты, поиск будет хуже.
- **Kimi K3 — неполный** (61/240), gpt-oss-20b — 14 пустых ответов; в итог входят только полученные ответы.
- **Задержки** — бесплатный уровень с общей очередью; на платном/своём хостинге они другие. Задержки первого прогона
  без поиска включали ожидание ограничителя, поэтому для таблицы сделан отдельный замер (40 вопросов на модель).
- Один прогон, temperature 0.2 — разброс между прогонами не измерялся; разница в 2–3 пункта — в пределах шума.

## Что дальше (предложения)

1. **Поиск, а не модель**: 21 % попадания нужной статьи в топ-5 — главное узкое место. Включить векторный поиск
   (ZANN_EMBEDDINGS), словарь синонимов «бытовое слово → термин закона», буст по `route`/категории; цель — ≥ 60 %.
2. **Проверка цитат обязательна** для любой открытой модели: статья должна существовать в корпусе, акт — быть
   казахстанским; «Жилищный кодекс», ГК РФ, Росреестр — блок-лист.
3. Кандидаты для Zann и дообучения: **Gemma 4 31B** (осторожная, быстрая, 31B — реально дообучить) и **Nemotron 3
   Ultra** (лучше всех цитирует с поиском, но много лишних деталей). Kimi K3 — перепроверить, когда каталог
   поднимет лимит.
4. Отдать юристу пилота выборку оценок судьи (≈ 50 ответов) — откалибровать судью и рубрику.
5. Казахский: отдельная выборка kk-ответов на проверку носителю языка.

```bash
git show origin/claude/ai-team:team/zann/bench/kz-v1.jsonl > /tmp/kz-v1.jsonl   # hidden отбросит сам раннер
python tools/zann/collect_laws.py --from-packs --codes Z1600000486 Z970000155_ K2300000224 Z1300000088 K1400000226 Z2200000178
python tools/zann/local_index.py                                     # → data/zann/index.sqlite
R="python tools/zann/bench_run.py --bench /tmp/kz-v1.jsonl --index-db sqlite:///data/zann/index.sqlite --date 2026-10-01"
$R --mode norag --models nvidia/nemotron-3-ultra-550b-a55b,nvidia/nemotron-3-super-120b-a12b,google/gemma-4-31b-it,meta/llama-3.2-90b-vision-instruct,openai/gpt-oss-20b,moonshotai/kimi-k3
$R --mode rag --models google/gemma-4-31b-it,nvidia/nemotron-3-ultra-550b-a55b
$R --judge google/gemma-4-31b-it                                     # оценки судьи в тот же сырой файл
$R --report-only                                                     # пересчитать и записать таблицы
```

Ключ — только из переменной среды `NVIDIA_API_KEY`; сырые ответы и таблицы — в `data/zann/` (не в git).
