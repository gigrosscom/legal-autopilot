## 2. Smart Bridge (sb.egov.kz)

### 2.1. Что это
Smart Bridge — витрина сервисов «электронного правительства». Бизнес подаёт на ней заявку на подключение к
сервису госоргана. Заявку рассматривает владелец сервиса. Сейчас в каталоге сотни сервисов.

### 2.2. Как ТОО получает доступ — по официальной инструкции
Источник — «Инструкция по работе по ролям пользователей, модуль „Витрина сервисов“» на sb.egov.kz (версия
02.2020, открыта 30.09.2026). Порядок:

1. **Вход в кабинет** sb.egov.kz по ЭЦП юрлица. Руководитель входит своей ЭЦП. Только он видит вкладку
   «Мои сотрудники» и может добавить сотрудников с ролью «Согласующий».
2. **Карточка информационной системы** («Мои информационные системы» → добавить): название на русском и
   казахском, ссылка на систему.
3. **Заявка на подключение к сервису.** Открыть паспорт сервиса. Если есть ссылка на «Инструкцию по созданию
   Клиент-коннектора» — выполнить её. Принять «Требования к взаимодействию с сервисом». Заполнить форму:
   - основание для подключения и файл с основанием (.doc, .docx, .pdf, архив);
   - ответственный (ФИО — из ЭЦП), телефон, e-mail;
   - информационная система (из карточки);
   - IP-адрес, порт и протокол системы — отдельно для тестовой и промышленной среды;
   - логин и пароли системы для шлюза ШЭП/ВШЭП (тест и прод);
   - контур взаимодействия (для нас — «вне ЕТС ГО») и есть ли VPN-туннель. Если нет — форма даёт
     технические условия VPN по IPsec (IKEv2, AES-256, SHA256 рекомендованы). Нужны модель шлюза и публичный IP;
   - **сертификат открытого ключа транспортной ЭЦП системы** (.cer / .crt);
   - для асинхронных сервисов — режим PULL или PUSH.
   Заявка подписывается ЭЦП.
4. **Согласование.** Владелец сервиса согласует, возвращает на доработку с комментарием или отказывает с причиной.
5. **Тестирование.** После подключения в тестовой среде владелец сервиса формирует **акт тестирования**
   (сценарий тестирования, дата ввода в промышленную эксплуатацию). Клиент согласует акт и подписывает ЭЦП.
6. **Промышленная среда** — с даты из акта. Дату может сдвинуть администратор ШЭП.

**Требования ИБ.** В форме заявки поле «Акт по результатам испытаний на соответствие требованиям информационной
безопасности» — **прикрепляют только государственные органы** (так в инструкции). Для частной ИС акт в форме не
требуется. Но владелец сервиса может поставить свои условия в «Требованиях к взаимодействию». Сервисы с
персональными данными из госбаз (ГБД ФЛ) для частных организаций идут через согласие человека — см. 2.4.

**Сроки.**
- Владелец сервиса даёт решение по заявке за 5 дней (НИТ, запуск платформы, 2020).
- В 2025 году Минцифры выносило проект: согласование тестирования — 2 рабочих дня, вход по mTLS, отдельный тип
  «сервис уведомлений» для упрощённого подключения (uchet.kz, 16.09.2025).
- **Важно:** старые Правила интеграции объектов информатизации «электронного правительства» (приказ № 123 от
  29.03.2018) утратили силу с 12.07.2026 — приказ № 368/НҚ от 01.07.2026. С 12.07.2026 действует Цифровой кодекс
  РК (№ 255-VIII от 09.01.2026). Текст новых правил интеграции мы не открыли — проверить до подачи. Ссылки в заявке
  на «Закон об информатизации» заменены на Цифровой кодекс.
- Наша оценка: 1–2 недели на одобрение, 1–3 недели на VPN и тест, итого **3–6 недель на один сервис**. Новые
  сервисы (подача в eOtinish, Судебный кабинет) — месяцы, срок неизвестен.
- Плата за подключение в официальных источниках не указана. Прошлые открытые источники говорят «бесплатно» — уточнить.

### 2.4. Персональные данные из госбаз
Данные человека из ГБД ФЛ частная организация получает только с его согласия, через государственный сервис
контроля доступа к персональным данным (Правила интеграции с ним — adilet V2200028786, редакцию проверить после
Цифрового кодекса). Пока это не нужно: ИИН и ФИО мы уже берём из сертификата ЭЦП человека при подписи.

**Что это значит для нас** (запрос ГБД ФЛ добавлен в заявку 5.4, приоритет низкий):
- Каждый запрос данных — только с согласия этого человека. Он подтверждает согласие в госсервисе (обычно SMS или
  eGov Mobile) в момент запроса. Без согласия ГБД ФЛ ничего не отдаёт.
- Нужно второе подключение: к сервису согласий, кроме самого ГБД ФЛ. Это отдельная заявка и отдельный срок.
- Для клиента это лишний шаг перед подачей. Брать данные «про запас» нельзя: только под конкретное обращение.
- Польза малая: ИИН и ФИО есть в сертификате ЭЦП, адрес клиент вводит сам. eOtinish при подаче через eGov сам
  подтягивает данные заявителя. Подключаем, только если оператор eOtinish потребует проверенный адрес.

## 3. Другие интеграции

### 3.1. eGov Mobile / вход и подпись по QR
- **Что даёт.** Вход и подпись документа с телефона, без NCALayer на компьютере. Большинство людей пользуются
  именно eGov Mobile.
- **Доступ.** Регистрация на Smart Bridge и заявка на сервис NITEC-S-5096. Оператор добавляет наши внешние адреса
  (api.konsilier.com). По Хабру «процесс может затянуться».
- **Что можно сейчас.** Код готов (`/auth/egov/...`, QR `mobileSign:`). Прописать `EGOV_ORG_BIN=260940036818` в
  настройках сервера. Для теста без Smart Bridge — сервис SIGEX (платный посредник) — только если владелец решит.
- **Проверить.** Кнопки «Открыть в eGov Mobile / eGov Business» на телефоне ведут на `mgovsign.page.link` и
  `egovbusiness.page.link`. Это Firebase Dynamic Links: Google отключил их 25.08.2025, ссылки отдают 404. Сам QR
  не затронут. Нужно узнать у НИТ новую ссылку для открытия приложения.
- **Срок.** 3–6 недель после подачи заявки.

### 3.2. eOtinish
- **Что даёт.** Подача обращения в госорган с нашего сайта и статус в деле.
- **Доступ.** Открытого API нет. На eotinish.kz подача — через eGov (веб, eGov Mobile) или ЦОН. В Smart Bridge
  есть только межведомственные сервисы. Путь — запрос нового сервиса владельцу ИС «Е-өтініштер» через Smart Bridge
  или письмом.
- **Что можно сейчас.** Блок «Подать онлайн» уже работает. Улучшить: готовый текст с получателем, выбор категории
  eOtinish в подсказке, напоминание «отметьте номер обращения».
- **Прецедент интеграции.** Documentolog (частная СЭД) подключён к eOtinish на стороне **получателя**: обращение
  передаётся организации с ЭЦП, ответ уходит заявителю обратно в eOtinish, заявитель видит все шаги на eotinish.kz.
  Значит, eOtinish умеет работать с частными системами. Но сервиса подачи **от заявителя** из частной системы мы
  не нашли.
- **Срок.** Неизвестен. Рассчитываем на месяцы. План подачи из дела — раздел 7.

### 3.3. Судебный кабинет (office.sud.kz)
- **Что даёт.** Подача исков и заявлений о судебном приказе из нашего дела, номер и статус.
- **Доступ.** На сайте кабинета API нет. Вход — ЭЦП или eGov. Поддержка — office@sud.kz. Прецедент: Debex
  подаёт заявления о судебном приказе в 700+ судов автоматически. Основание их доступа на сайте не указано. Путь —
  письмо в Департамент по обеспечению деятельности судов при Верховном Суде (текст — раздел 5.6).
- **Что можно сейчас.** Ссылка и инструкция в блоке «Подать онлайн» (есть). Готовить пакет файлов в форматах,
  которые принимает кабинет.
- **Срок.** Неизвестен, месяцы.

### 3.4. Госзакупки — goszakup.gov.kz, OWS API v3
- **Что даёт.** Бета-сценарий тендера: по номеру объявления подтянуть лоты, сроки, заказчика, требования,
  проверить поставщика в реестре недобросовестных (РНУ). Меньше ручного ввода и ошибок.
- **Доступ.** REST `https://ows.goszakup.gov.kz/v3/` и GraphQL `.../v3/graphql`. Только чтение. Токен выдаёт
  АО «Центр электронных финансов» по письму с описанием, как используем данные. Токен на 1 год. Нужна регистрация
  организации на портале госзакупок; продлевает токен администратор организации в профиле («Выдача токена для
  разработчиков»). Данные: объявления, лоты, договоры, участники, РНУ, годовые планы, заявки.
- **Что можно сейчас.** Зарегистрировать ТОО на портале (ЭЦП юрлица). Отправить письмо в ЦЭФ. Написать клиент
  API с тестами на записанных ответах.
- **Срок.** Письмо — 1 день. Токен — 1–3 недели (оценка). Интеграция в сценарий — 2–3 дня после токена.
- **Заметка.** goszakup.gov.kz перенаправляет документацию на old.goszakup.gov.kz — сверить адреса API при старте.

### 3.5. NCALayer и NCANode (уже есть)
- **Что даёт.** Вход и подпись ЭЦП на компьютере. Проверка подписи, цепочки до корней НУЦ РК и отзыва (OCSP).
- **Доступ.** Не нужен. NCALayer ставит сам пользователь (ncl.pki.gov.kz; Windows, Linux, macOS). NCANode — наш
  сервер, образ `malikzh/ncanode:3.5.0` (актуальный, от 03.09.2026).
- **Что сделать.** Починить проверку подписи (раздел 6).

### 3.6. 1С и бухгалтерия (для B2B)
- **Что даёт.** Для бизнеса: взять из 1С должника, сумму долга, договор и акты — и сразу сделать претензию.
  Обратно — отметить в 1С, что претензия отправлена.
- **Доступ.** Договор с 1С не нужен. У клиента своя база 1С:Бухгалтерия для Казахстана. Платформа 1С:Предприятие
  с версии 8.3.5 даёт стандартный REST-интерфейс OData (справочники, документы, регистры). Клиент публикует его и
  выдаёт нам логин только на чтение. Вариант проще — выгрузка XML/Excel (акт сверки, оборотка) и загрузка в дело.
- **Что можно сейчас.** Загрузка файлов уже есть: сервис читает PDF, фото, DOCX. Добавить разбор Excel-акта
  сверки. OData-коннектор — только под первого B2B-клиента.
- **Срок.** Разбор акта сверки — 2–3 дня. Коннектор OData — 1–2 недели под конкретную базу.

## 6. Почему не отвечает проверка ЭЦП (NCANode)

**Что видно в коде.**
- API ходит в NCANode по адресу `http://ncanode:14579` — задан прямо в `deploy/docker-compose.prod.yml`
  (`NCANODE_URL`). Порт совпадает с портом NCANode по умолчанию (14579). Адрес верный.
- NCANode — контейнер `malikzh/ncanode:3.5.0`, `mem_limit: 1g`, без healthcheck. Порт наружу не открыт.
- Проверка после деплоя (`deploy/update.sh`) шлёт пустую подпись на `/cms/verify` с таймаутом 20 с. 29.09 ответ
  был `ncanode=400` — сервис жил. 30.09 — `ConnectTimeout`. Файл compose с 27.09 не менялся.

**Вероятная причина.** Контейнер NCANode завис или перегружен, а не ошибка адреса. `ConnectTimeout` значит: TCP-
соединение не принимается совсем. Так бывает, когда очередь соединений Java-сервера забита. Самое вероятное:
- NCANode при старте и раз в сутки (TTL 1440 мин) скачивает большие списки отзыва (CRL) с `crl.pki.gov.kz` и
  сертификаты с `pki.gov.kz`, а при каждой проверке ходит в `ocsp.pki.gov.kz`. Если эти адреса с нашей ВМ
  недоступны или медленные, потоки сервера висят, и новые соединения не принимаются.
- Лимит 1 ГБ: Java берёт под кучу около четверти лимита (~256 МБ). Полный CRL НУЦ большой — возможны нехватка
  памяти, долгие паузы или падения по кругу.

**Как проверить и починить (нужен доступ к серверу, после «да» владельца):**
1. `docker compose -f deploy/docker-compose.prod.yml ps ncanode` и `logs --tail 200 ncanode`;
   `docker inspect` — поля `OOMKilled` и `RestartCount`.
2. С ВМ: `curl -m 10 -I http://crl.pki.gov.kz/` и `http://ocsp.pki.gov.kz/` — есть ли выход к НУЦ.
3. Быстро: `docker compose restart ncanode`.
4. Надёжно (PR): healthcheck по `/actuator/health`, `mem_limit: 2g` и явный `-Xmx`, в проверке после деплоя ждать
   готовности NCANode до 2 минут. Если выхода к pki.gov.kz нет — `NCANODE_PROXY_URL` или открыть исходящий трафик.

Пока NCANode не отвечает, вход и подпись ЭЦП возвращают `verifier_unavailable`.

**Обновление 30.09.2026 — PR #95 и #97 слиты в деплойную ветку `claude/zealous-volta-a3ipv6`.**
- **PR #95 (`ncanode-fix`, 03f94de).** В `deploy/update.sh`: если после деплоя проверка ЭЦП не ответила, скрипт пишет
  в журнал состояние контейнера, память ВМ и последние строки лога NCANode. Затем один раз перезапускает NCANode,
  ждёт 2 минуты и проверяет снова.
- **PR #97 (`ncanode-autoheal`, 4fffae0, слияние 97bb790).** В `deploy/update.sh`, при каждом запуске таймера (раз в
  несколько минут): если Docker пометил контейнер NCANode как `unhealthy`, скрипт его перезапускает (`docker restart`,
  таймаут 60 с). Причина: 30.09 NCANode завис примерно через 2 дня работы, Docker пометил его `unhealthy`, но сам не
  перезапускает.
- **По карте продукта** (`team/product.md`, журнал 30.09): ЭЦП снова работает, NCANode перезапускается сам.

**Снят ли блокер для подачи обращений? Частично.**
- Снято: долгий простой. Зависший NCANode теперь поднимается сам за несколько минут.
- Не снято: причина зависания. `mem_limit` по-прежнему 1 ГБ. Своего healthcheck в `docker-compose.prod.yml` нет —
  автоперезапуск опирается на healthcheck внутри образа. Мы проверили конфиг образа `malikzh/ncanode:3.5.0` (amd64) в
  Docker Hub: `wget http://127.0.0.1:14579/actuator/health`, раз в 20 с, таймаут 30 с, 7 попыток. В образе задано
  `JAVA_OPTS=-Xms128m -Xmx512m`, но запуск — `java -jar NCANode.jar` без этой переменной. Похоже, она не
  применяется, и куча — около четверти лимита (~256 МБ). Проверить на сервере.
- Остаётся окно отказа: до ~6 минут, пока Docker признает контейнер `unhealthy`, плюс минуты до запуска таймера и
  1–2 минуты загрузки списков отзыва. В это время подпись клиента не проверяется.
- **Что нужно до запуска подачи:** (1) свой healthcheck в compose и `mem_limit: 2g` с явным `-Xmx`; (2) оповещение
  владельцу или дежурной сессии, если NCANode перезапускался чаще раза в сутки; (3) в потоке подачи — сначала
  сохранить подписанную CMS, потом проверять; при `verifier_unavailable` — повторить проверку позже, а не терять
  подпись клиента (см. 7.2).

## 7. Подача обращений клиента из дела

Решение владельца 30.09.2026. Цель: клиент подаёт обращение в eOtinish или госорган прямо из своего дела в
Konsiliér AI, подписав его **своей** ЭЦП. Мы — технический канал передачи, а не представитель. Это ставка 1 из
`team/strategy/10x-value.md`: «ведение дела до результата» — подача с ЭЦП, доказательство отправки, сроки,
эскалации.

### 7.1. Путь клиента и этапы

1. Клиент готовит документ в деле (есть).
2. Клиент подписывает его своей ЭЦП или в eGov Mobile (7.2).
3. Клиент нажимает «Подать». Дальше — по этапам:
   - **Этап 1 — ручной мост (без внешних доступов, 1–2 недели).** Мы даём готовый текст, орган и категорию
     eOtinish, PDF и подписанный пакет. Клиент подаёт на eotinish.kz сам (подпись там — снова его ЭЦП или eGov).
     Потом возвращается в дело: вводит номер обращения и дату, загружает квитанцию или снимок экрана. Наша подпись
     в этом случае — доказательство текста и времени, а не подача.
   - **Этап 2 — передача через сервис eOtinish** (после заявки 5.5; срок — месяцы). Кнопка «Подать» передаёт
     подписанную CMS в eOtinish. Номер и квитанция приходят сами.
   - **Этап 3 — статус и ответ сами** (ORGB7-S-5159 или метод 2 из 5.5).
4. Для адресатов вне eOtinish (компании, банки, работодатели) — клиент отправляет сам; опция Казпочты отменена владельцем 30.09.
5. Доказательство подачи хранится в деле (7.3). Срок ответа и напоминания — как сейчас, от даты подачи (7.4).

### 7.2. Подпись клиента (CMS)

**NCALayer — компьютер.** Страница обращается к NCALayer на компьютере клиента. Клиент выбирает свой ключ.
NCALayer возвращает CMS: подпись вместе с документом внутри. В коде есть (`api/signing.py`, способ `ncalayer`).
На телефоне NCALayer нет.

**eGov Mobile по QR — NITEC-S-5096.** Мы показываем QR `mobileSign:<ссылка>`. Приложение eGov Mobile (или eGov
Business) скачивает документ по одноразовой ссылке с `api.konsilier.com`. Клиент подписывает в приложении.
Приложение отправляет CMS обратно к нам. Код есть (`/auth/egov/...`, способ `egov`), но выключен: нужен доступ к
NITEC-S-5096 через Smart Bridge и `EGOV_ORG_BIN` в настройках сервера.
- **Проблема на телефоне.** Если клиент уже на телефоне, QR сканировать нечем. Нужна ссылка «Открыть в eGov
  Mobile». Наши кнопки ведут на `mgovsign.page.link` и `egovbusiness.page.link`. Это Firebase Dynamic Links — Google
  отключил их 25.08.2025, ссылки отдают 404. Нужна новая ссылка от НИТ (вопрос в заявку NITEC-S-5096). До этого на
  телефоне остаётся только NCALayer на компьютере или второй телефон.

**Что делает наш NCANode.** Только проверяет, не подписывает и не отправляет. Проверка: подпись верна; хеш документа
совпадает; сертификат выдан НУЦ РК (цепочка до корня); сертификат не отозван (OCSP или список отзыва); ключ — для
подписи, а не для входа. Из сертификата берём ИИН и ФИО подписанта. ИИН храним только как HMAC.

**Метка времени.** Для доказательства важна метка времени НУЦ (TSP) внутри CMS. Проверить: ставят ли её NCALayer и
eGov Mobile в нашем вызове. Если нет — добавить запрос метки (в NCALayer есть такая опция; проверить).

**Блокер — NCANode.** 30.09 проверка висела (`ConnectTimeout`). После PR #95 и #97 NCANode перезапускается сам, но
причина зависания не найдена (раздел 6). Правило для подачи: **сначала сохранить CMS клиента, потом проверять.** Если
NCANode не ответил — повторить проверку через минуту и показать «Проверяем подпись». Подпись клиента не теряем.
Кнопку «Подать» открываем только после успешной проверки.

### 7.3. Доказательство подачи: что и где хранить

**Где.** Метаданные — в PostgreSQL. Файлы — в нашем файловом хранилище (S3-совместимое, как `cms_key` сейчас),
в Казахстане. Файлы не перезаписываем: новая версия — новый файл. У каждого файла в базе — SHA-256. Каждое событие —
в журнал действий (`AuditLog`). Срок хранения — решает владелец (предложение: 5 лет после закрытия дела).

**Новая сущность «Подача»** (одна на каждую отправку документа адресату; связана с шагом дела `Action`).

| Поле | Что хранит |
|---|---|
| `id`, `case_id`, `action_id` | Дело и шаг дела |
| `signature_id` | Ссылка на `DocumentSignature` (CMS, `doc_sha256`, способ, время подписи — уже есть) |
| `channel` | `eotinish_manual` · `eotinish_api` · `kazpost_hybrid` · `email` · `court_cabinet` · `in_person` |
| `addressee` | Орган или организация: название, БИН, адрес, категория eOtinish |
| `status` | `prepared` → `signed` → `sending` → `sent` → `registered` → `delivered` → `answered` · `failed` · `cancelled` |
| `consent_text_version`, `consent_at` | Какой текст «Я поручаю передать мой подписанный документ…» клиент подтвердил и когда |
| `package_key`, `package_sha256` | Что именно ушло: PDF, CMS, вложения — одним архивом |
| `attachments` | Список вложений: имя, размер, SHA-256 |
| `tsp_time`, `tsp_key` | Время из метки TSP НУЦ, если есть, и сама метка |
| `verify_result_key`, `verified_at` | Сырой ответ NCANode и время проверки (с результатом OCSP) |
| `sent_at` | Время нашей передачи (UTC, часы сервера синхронизированы) |
| `external_id` | Номер обращения eOtinish или ШПИ Казпочты |
| `external_registered_at` | Дата и время регистрации у адресата |
| `receipt_key`, `receipt_sha256`, `receipt_source` | Квитанция (PDF, ответ сервиса или снимок экрана) и откуда: `api` · `client_upload` · `client_entered` |
| `delivery_notice_key`, `delivered_at` | Уведомление о вручении (Казпочта) и дата вручения |
| `response_due` | Ссылка на `Deadline` (срок ответа — уже есть) |
| `response_received_at`, `response_key`, `response_sha256` | Ответ органа: дата и файл |
| `cost_kzt` | Сколько стоила отправка (для почты) |

**Сущность «Событие подачи»** — история: `filing_id`, `at`, `kind` (подписано, передано, зарегистрировано,
статус, вручено, ответ, ошибка), `source` (`api` · `client` · `ops`), `payload_key`, `payload_sha256`.

**Что видит клиент.** Карточка «Доказательство подачи» в деле: номер, дата, кому, статус. Кнопка «Скачать пакет»:
PDF, CMS, квитанция и файл с хешами. Этот пакет клиент может отдать юристу или в суд.

Связь с тем, что есть: `Action.submitted_at` и `submitted_via` заполняются из «Подачи». Напоминания работают как сейчас.

### 7.4. Статус и ответ органа

- **Автоматически — пока нельзя.** ORGB7-S-5159 в каталоге Smart Bridge — межведомственный. Сервиса статуса для
  частных систем мы не нашли. Просим его в заявке (5.4, 5.5). Срок — неизвестен.
- **Сейчас — клиент сам.** Клиент вводит номер и дату (из SMS, письма или кабинета eOtinish). Мы ставим срок ответа
  и напоминаем — это уже работает после «Документ подан» (`Deadline`, `remind_before_days`). В день срока спрашиваем:
  «Ответ пришёл?» — «Да» (загрузить PDF ответа; поля `response_*` уже есть в `Action`) или «Нет» (готовим следующий
  шаг: жалоба на бездействие, вышестоящий орган).
- **Позже.** Адрес дела для пересылки писем eOtinish (клиент пересылает уведомление — мы достаём номер и статус).
  Только после отдельного решения.
- Сроки рассмотрения берём из пакета сценариев по АППК, не из памяти. Проверяет юрист.

### 7.5. Альтернативный канал: Казпочта, гибридная почта (ГЭП)

> **Отменено.** Решение владельца 30.09.2026: опцию «Отправить заказным письмом» через Казпочту убрать полностью. Раздел оставлен как справка; не делаем.

**Что это.** «Гибридная электронная почта» (ГЭП) АО «Казпочта»: отправитель передаёт электронный документ и адрес,
Казпочта печатает, кладёт в конверт и доставляет. Срок по FAQ Казпочты — «в течение 1-2 рабочих дней с момента
отправки»; на странице услуги — «в течение двух рабочих дней». Для сравнения: обычное заказное письмо между
областными центрами идёт 2–8 дней (таблица сроков Казпочты с 01.01.2026). Печать только чёрно-белая. За 2020 год
доставлено больше 2,3 млн гибридных писем; пользуются физлица, бизнес и в основном госорганы (SK News, 2021).

**Цены** (официальный прейскурант Казпочты «для розничного, корпоративного бизнеса с 01 января 2026 года», п. 1.5
«Тарифы на услуги по пересылке гибридного отправления в пределах РК», тенге с НДС; те же цифры — на странице услуги):

| Услуга | Тариф |
|---|---|
| Пересылка регистрируемого гибридного отправления | 400 ₸ |
| Уведомление о получении почтового отправления | 300 ₸ |
| Предпочтовая обработка (печать, конверт): до 50 г | 210 ₸ |
| 50–100 г | 300 ₸ |
| 101–250 г | 600 ₸ |
| 251–500 г | 960 ₸ |

Предпочтовая обработка и уведомление в прейскуранте — «Дополнительные услуги», то есть добавляются к 400 ₸. Вес в
листах по сайту post.kz: до 50 г — 1–5 листов А4; 51–100 г — 6–10 листов; 101–250 г — 11–25 листов.

| Письмо с уведомлением о получении | Себестоимость для нас |
|---|---|
| 1–5 листов | 400 + 210 + 300 = **910 ₸** |
| 6–10 листов | 400 + 300 + 300 = **1 000 ₸** |

**Правовая основа.** Закон РК «О почте» (№ 498-V), ст. 1: гибридное почтовое отправление — «электронное письмо
(сообщение), принятое оператором почты к пересылке и доставляемое адресату в виде письма (почтовой карточки)» (п. 6);
регистрируемое отправление принимается «с выдачей отправителю подтверждающего документа на бумажном носителе либо в
электронной форме» (п. 51). Уведомление о получении — дополнительная платная услуга, на бумаге и (или) в
электронной форме (по выдаче поиска, текст статьи не открывали).

**Доступ и API.**
- Физлицо может отправить гибридное письмо само на post.kz: вход, ИИН и ФИО в профиле, загрузка PDF (до 10 МБ, не
  больше 386 страниц), оплата, квитанция. Для юрлица сайт пишет: «обратиться в отделение АО "Казпочты" для
  заключения договора на юридическое лицо».
- Кабинет ГЭП — `newgep.kazpost.kz`: письма и вложения, рассылки, отчёт ГЭП, поиск формы 103.
- Open API Казпочты (`open.post.kz`): адресные бланки, вызов курьера, справочники. Боевой токен — «необходимо
  связаться с менеджером отдела продаж». Старый SOAP-модуль (`rates.kazpost.kz`): тарифы, адресные ярлыки, ШПИ,
  электронная форма 103, отделения.
- **Публичного API для ГЭП мы не нашли.** Кнопка «Подать заявку» на странице ГЭП ведёт на
  `post.kz/services/postal/all/hybridmail`. Путь — договор с Казпочтой и доступ через менеджера.

**Вопросы до договора.**
1. **Кто отправитель.** В ГЭП отправитель — владелец кабинета или договора. Владелец 30.09 утвердил пилот: мы
   передаём подписанный клиентом документ в ГЭП по нашему договору (7.5.1). Вопрос к Казпочте: можно ли указать
   отправителем в письме и в уведомлении самого клиента (его ФИО и обратный адрес), а ТОО — только плательщиком по
   договору. Для претензии важно, чтобы отправителем был клиент. Если нельзя — решает владелец как юрист.
2. **Подпись на бумаге.** Распечатка не несёт ЭЦП и собственноручной подписи. Можно печатать отметку «Подписано ЭЦП
   <ФИО>, <дата>» и QR на проверку CMS. Годится ли такая претензия — решает юрист.
3. Уведомление о вручении: в каком виде приходит по ГЭП (бумага, скан, статус) — см. 7.5.1.

бумаге или в электронной форме. Значит, по умолчанию бумажное уведомление с подписью получателя едет на обратный
адрес отправителя. Варианты для нас:
- (а) обратный адрес — наш офис: получаем бумагу, сканируем, кладём в дело, оригинал храним или отдаём клиенту;
- (б) обратный адрес — клиента: клиент фотографирует уведомление и загружает в дело;
- (в) лучше всего — электронное уведомление или скан в кабинете ГЭП или в бесплатном отчёте о доставке. Спросить
  при договоре.
До ответа Казпочты в деле храним: ШПИ, квитанцию, статусы трекинга, отчёт о доставке, затем уведомление.

**Маржа на одно письмо** (оценка). Себестоимость — тарифы выше. Комиссия Kaspi — 0,95–1,35 % от цены. Налог —
4 % с дохода, если ТОО на упрощённой декларации (`team/finance.md`, проверить у бухгалтера). Kazpost берёт цены с
НДС; зачесть НДС ТОО на упрощёнке не может.

| Письмо | Себестоимость | Цена 1 500 ₸: Kaspi / налог / **маржа** | Цена 2 000 ₸: Kaspi / налог / **маржа** |
|---|---|---|---|
| 1–5 листов | 910 ₸ | 14–20 / 60 / **≈ 510 ₸ (34 %)** | 19–27 / 80 / **≈ 985 ₸ (49 %)** |
| 6–10 листов | 1 000 ₸ | 14–20 / 60 / **≈ 420 ₸ (28 %)** | 19–27 / 80 / **≈ 895 ₸ (45 %)** |
| 11–25 листов | 1 300 ₸ | 14–20 / 60 / **≈ 120 ₸ (8 %)** | 19–27 / 80 / **≈ 595 ₸ (30 %)** |

Не учтено: время на скан бумажного уведомления (вариант а), возвраты (письмо не вручено), отчёт о возврате 120 ₸.
Предложение: 1 500 ₸ — за письмо до 10 листов; 2 000 ₸ — за 11–25 листов; больше 25 — отдельная цена. Риск: физлицо
может само отправить то же письмо на post.kz за 910 ₸. Наша ценность — готовый документ, одна кнопка, доказательство
в деле, срок ответа и напоминания.

**Поток пилота (после договора).**
1. Клиент подписывает документ ЭЦП (7.2). NCANode проверяет подпись.
2. Клиент видит адресата, число листов, цену и текст согласия «Я поручаю передать мой подписанный документ в
   Казпочту для отправки заказным письмом». Платит через Kaspi.
3. Мы собираем PDF для печати: документ, отметка «Подписано ЭЦП <ФИО>, <дата и время>», QR на проверку подписи.
4. Загружаем PDF в кабинет ГЭП по нашему договору (на пилоте — вручную, дежурный в /ops; позже — API, если Казпочта даст).
5. В «Подачу» (7.3) пишем: канал `kazpost_hybrid`, ШПИ, квитанцию, цену, время.
6. Следим за статусом по ШПИ. Уведомление о вручении и отчёт о доставке кладём в дело. Дата вручения — начало
   срока ответа; напоминания — как сейчас.
7. Если не вручено — отчёт о возврате, клиенту — следующий шаг.

**Что нужно до запуска.** Договор с Казпочтой на ТОО; ответы Казпочты: отправитель в письме, формат уведомления,
API или пакетная загрузка, скидки по объёму; решение юриста о печатной копии без собственноручной подписи; окончательная
цена для клиента.
